# F 키의 주인 (InteractKey)

[문서 목차](../README.md) · [두 손 (설계)](Hands.md) · [손가락질과 찌르기](Poke.md)

상호작용 키(F, 키 설정의 `Player/Interact`)가 지금 누구의 것인지를 한 곳이 정한다. 2026-11-18에 세웠다.

사용자(2026-11-18, 8번 항목의 뜻): "바닥에 떨어진 체력킷, 쉴드쉘이 서포트의 구조물 설치 판정을 막는다". 설치 판정 쪽은 [Placement](../../Assets/_Project/Scripts/Classes/Deployables/Placement.cs)가 맡았고, 그 코드를 읽다가 다른 뿌리가 나왔다. **F가 누구 것인지 아는 곳이 없었다.** 처형, 줍기, 부활, 사다리, 임무 버튼, 문, 상점, 서포트의 보급과 수리, 데탕트의 치료, 탄약 상자, 핑이 저마다 키를 직접 읽고, 저마다 "내가 비켜 줘야 하는 남들"의 목록을 따로 들고 있었다. 목록끼리 서로 달랐다. 그래서

- 한 번 눌러 두 가지가 됐다: 탄약 상자 보급과 줍기, 서포트의 구조물 종류 바꾸기와 총 줍기·부활·처형·핑, 데탕트의 치료 수락과 줍기.
- 할 수 없는 것이 키를 쥐고 있었다: 체력이 가득할 때 바라본 구급상자(쉴드가 있을 때의 쉴드 셀)가 그 뒤의 바리케이드 수리, 동료 보급, 문, 타워 스캐너까지 막았다. 좀비는 바리케이드 앞에서 죽고 물건도 거기 떨어진다.

## 규칙

F는 **한 번에 한 가지**를 한다. 플레이어 앞에 F로 할 수 있는 것이 여럿이면 [표](../../Assets/_Project/Data/Resources/Tables/Player/InteractKey.csv)에서 가장 위에 있는 것 하나가 그 누름을 받고, 화면에도 그것 하나만 [F] 안내로 보인다.

1. **나선다.** F로 할 일이 있는 기능은 그런 프레임마다 `InteractKey.Offer(id, …)`로 말한다. 다시 말하지 않으면 그 제안은 끝난 것이다(등록하고 잊는 것이 없다. 지속 효과의 `TimedEffects.Report`와 같은 방식).
2. **주인이 고른다.** 서 있는 제안 가운데 표의 순서로 맨 앞이면서 지금 할 수 있는 것이 F를 가진다.
3. **거절은 넘긴다.** 지금 할 수 없는 제안은 까닭과 함께 나선다(`refusal`). 거절한 것은 누름을 가져가지 않고 다음 차례로 넘긴다. 앞에 누름을 가져갈 것이 없는 동안은 거절 안내가 회색으로 그대로 보인다. 그래서 화면은 "구급상자는 왜 안 주워지는지"와 "F가 대신 무엇을 하는지"를 같이 말한다.
4. **주인이 "네 것"이라 할 때만 움직인다.** 누르는 순간에 하는 일은 `InteractKey.Pressed(id)`, 누르고 있는 동안 하는 일은 `InteractKey.Held(id)`, 안내를 보여도 되는지는 `InteractKey.Shows(id)`.
5. **한 번의 누름은 한 가지 일.** 누르는 순간에 하는 일(줍기, 문, 처형 …)에 준 누름은 거기서 끝난다. 키를 계속 누르고 있어도 다른 일이 시작되지 않는다. 누르고 있는 동안 하는 일(부활, 수리, 스캐너, 부활술)에 갔거나 아무에게도 가지 않은 누름은 열려 있어서, 그런 일이 맨 앞에 서면 이어받는다: F를 누른 채 쓰러진 동료에게 다가가면 닿았을 때 일으키기 시작하고, 수리하던 중에 옆에서 동료가 쓰러지면 일으키기가 먼저다.
6. **키를 누를 때 화면에 보이던 것이 받는다.** 지난 프레임에 나선 것들이 이번 프레임의 누름을 정한다. 누구의 Update가 먼저 도는지와 상관없이 모두가 같은 답을 듣는다.
7. **키는 몸의 것이다.** 이 PC의 플레이어가 없거나 움직일 수 없으면(죽음, 진행 중인 판에 난입해 대기 중) 무엇이 나섰든 서지 못하고, 누름도 누르고 있음도 없다. 기능이 저마다 "죽었으면 나서지 않는다"를 기억할 필요가 없다. 처음에는 23곳이 각자 그 검사를 들고 있었고 그중 사다리 위 한 곳이 빠져 있었다. 쓰러진 것은 살아 있는 몸이라 여기서 막지 않는다: 쓰러진 채 무엇을 할 수 있는지는 기능마다의 규칙이다.

키가 애초에 게임의 것인지(화면이 키를 쥐었는지, 창이 뒤에 있는지)는 이보다 앞선 질문이고 [InputHold](../../Assets/_Project/Scripts/UI/Shared/InputHold.cs)·InputFocus·KeyBindings의 것이다. 화면이 제 닫는 키로 F를 읽는 것(상점, 허브의 옷 갈아입기: `KeyBindings.Pressed(path, 화면)`)은 여기 오지 않는다. 화면을 닫은 F는 그 프레임에 게임으로 새지 않는다(키가 앞 프레임에도 게임의 것이었을 때만 누름으로 친다).

## 기능을 더하려면 (모드 포함)

```csharp
public const string OfferId = "mymod.lever";                       // 표에 같은 id로 한 줄을 더한다

private void Update()
{
    var lever = LeverInReach();                                     // 지금 F로 할 일이 있는가 (기능 자신의 규칙)
    if (lever != null) InteractKey.Offer(OfferId, target: lever);   // 있으면 프레임마다 말한다
    prompt.SetActive(lever != null && InteractKey.Shows(OfferId));  // 안내는 주인이 보여도 된다고 할 때만
    if (lever != null && InteractKey.Pressed(OfferId)) lever.Pull();
}
```

- 지금 못 하는 까닭이 있으면 `refusal: "글자"`를 넘긴다. 안내를 회색으로 그리는 것은 기능의 몫이다.
- 누르고 있는 동안 하는 일이면 `held: true`로 나서고 `InteractKey.Held(id)`를 묻는다.
- 다른 기능이 F를 원하는지 묻지 않는다. 그 질문이 없어진 것이 이 구조의 요점이다.
- 표에 줄이 없으면 `other` 자리에 서고 로그에 한 번 알린다.

## 플레이 없이 확인하기

- `Logs/interact-key-check.txt`: 에디터가 스스로 쓰는 보고서([InteractKeyCheck](../../Assets/_Project/Scripts/UI/Shared/InteractKeyCheck.cs)). 게임의 규칙 그 자체(`InteractKey`의 함수들)를 게임이 읽은 표 위에서 돌린다. 첫 줄이 `ALL KEPT`이면 통과다. 스크립트가 다시 읽힐 때마다와 플레이가 끝날 때마다 저절로 돌고, 메뉴 ENFILADE → 입력 → F 키 규칙 점검, 또는 `Temp/enfilade-interactcheck.request` 파일을 만들면 다시 돈다. 무엇을 보는가: 게임이 나서는 23가지가 모두 표에 줄이 있고 자리가 겹치지 않는지, 거절한 줍기가 그 뒤의 17가지 각각을 막지 않는지, 서포트의 계획 중에는 다른 제안이 몇이 서 있든 F가 계획의 것인지, 전에 뜻이 있던 차례가 남아 있는지, 누름 하나가 일 하나인지, 10만 가지 상황에서 맨 앞이 하나이고 표의 순서대로인지.
- `python Tools/Checks/interact_key_check.py`: 규칙의 순수 함수(`Before`, `Lead`, `Shown`, `Step`, `HeldBy`, `Read`)를 파이썬으로 옮겨 **같은 표** 위에서 돌린다. 표의 줄마다 나서는 코드가 있는지, 코드가 나서는 id마다 줄이 있는지, 주인 말고 키를 직접 읽는 곳이 없는지도 스크립트를 읽어 확인한다. 규칙을 바꾸면 이 파일도 같이 바꾼다.
- `Logs/interact.txt`: 플레이 중 F를 누를 때마다 한 줄. 누가 가져갔는지(`GOT IT`), 누가 거절했는지(`refuses "까닭"`), 누가 뒤에서 기다렸는지(`behind`). 눌려 있던 키를 이어받으면 `HOLD →`. 에디터와 개발 빌드에서만 쓴다.
- 콘솔 `/interact`: 게임이 읽은 순서(모드가 얹은 줄 포함), 지금 서 있는 제안, 마지막 누름.

## 바뀐 동작

| 상황 | 전 | 지금 |
| --- | --- | --- |
| 체력이 가득한데 구급상자가 보이는 자리에서 바리케이드 수리·동료 보급·문·스캐너·데탕트 치료 | F가 아무것도 안 함 | 회색 줍기 안내는 그대로 보이고 F는 그 뒤의 일을 한다 |
| 서포트가 클래스 키를 누른 채 F | 종류가 바뀌면서 바라본 총도 줍고, 부활·처형·핑도 같이 | 종류만 바뀐다 (던지기 카드면 꾸러미만 던진다) |
| 탄약 상자를 조준하고 F, 옆에 줍기 물건 | 둘 다 | 표의 순서로 하나 (줍기가 먼저, 다시 누르면 상자) |
| 데탕트의 치료 제안에 F, 구급상자를 보는 중 | 수락하면서 구급상자도 주움 | 수락만 (다시 누르면 줍기) |
| 줍기에 F를 누른 채로 있음, 뒤에 바리케이드 | 줍고 나서 망치가 나옴 | 줍기만 |
| 타워 스캐너 옆에 쓰러진 동료 | F 하나로 손도 대고 부활도 진행 | 부활이 먼저, 일으킨 뒤 손 |
| 처형·부활·계획이 F를 가진 동안 다른 [F] 안내 | 일부는 같이 보임 | 가져갈 하나만 보인다 |

## 남은 일

- 안내를 그리는 곳은 아직 여섯 군데다(줍기 판, 캠페인 줄, 화면 아래 줄, 처형 안내, 연쇄 안내, 사다리 안내). 누가 보여도 되는지는 이제 한 곳이 답하지만 그리는 일은 각자 한다. 제안이 글자까지 넘기고 한 곳이 그리게 하면 [화면 아래 줄](../../Assets/_Project/Scripts/Classes/Detente/DetenteLooks.cs)을 셋이 나눠 쓰며 서로 지워 주는 코드도 없어진다.
- `SupportKit.HandsFree`와 `DetenteKit.HandsFree`는 이제 정말 손의 질문만 남았고(처형 중인가, 상점이 열렸나) 글자가 같다. [두 손의 주인](Hands.md)이 생기면 거기로 간다.
